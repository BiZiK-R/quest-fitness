# PRD: Quest Fitness

*Внутренний инструмент зала Quest Fitness (рабочее название продукта совпадает с брендом зала).*

## 0. Назначение документа

Этот PRD — ориентир для PM, заказчика и дальнейших workflow (UX, архитектура, эпики, реализация). Термины из **Глоссария** обязательны для всех downstream-артефактов. Возможности описаны как поведение продукта; стек и транспорт — в `addendum.md` и на этапе architecture. Живой якорь проекта: `docs/project-spec.md`. Дизайн-направление «Гильдия»: `design-brief-guild.md` и `docs/design-refs/`.

## 1. Vision

Quest Fitness — цифровой дневник и общее рабочее место **пула тренеров** одного зала: общая база клиентов, общие программы, проведение тренировки в зале с логом подходов, циклы и доступ клиента к своей истории.

Это не кабинет «один тренер — свои клиенты». В зале есть **пул клиентов** и **пул тренеров**: любой тренер из пула может открыть любого клиента, вести/править программу и проводить сессию. Фокус — тренировочный процесс и совместный дневник, а не биллинг и не SaaS для чужих залов.

Интерфейс — **веб-приложение**, mobile-first, минималистичный, для обычных людей в зале; визуальный язык — бренд «Гильдия» (тёплый светлый фон, уголь, красный акцент), без визуального шума.

## 2. Target User

### 2.1 Jobs To Be Done

- **Тренер / админ-тренер:** из общего пула взять любого клиента, назначить или продолжить сохранённую программу, в зале нажать «Начать» и вести подходы; при необходимости править то, что завели коллеги.
- **Клиент зала:** видеть свои тренировки и прогресс; при необходимости вписать питание и замеры (на этапе, когда эти разделы подключены). Ему всё равно, какой тренер из пула провёл занятие — Дневник один.
- **Админ (заказчик):** то же, что тренер, плюс привилегии (например ачивки и управление пулом тренеров).

### 2.2 Non-Users (v1)

- Другие залы / франшизы / публичный self-serve SaaS.
- Бухгалтерия, расчёт ЗП и выручки.
- Клиенты, самостоятельно бронирующие слоты без тренера.

### 2.3 Key User Journeys

**UJ-1. Тренер из пула проводит тренировку любого клиента.**  
Тренер открывает Клиента из общего Пула клиентов (не «своего» списка). Берёт уже сохранённую программу или задаёт/правит её, у Тренировки в Ожидании жмёт «Начать», логирует подходы (вес, повторения, RPE), суперсеты и отдых, завершает Сессию. Другой тренер завтра может продолжить того же Клиента. Клиенту достаточно истории после — live не обязателен.

**UJ-2. Тренер собирает программу и цикл (общие артефакты зала).**  
Тренер создаёт Шаблон тренировки, собирает Макроцикл и назначает Клиенту Тренировки. Коллеги из Пула тренеров видят и при необходимости редактируют эти назначения и шаблоны. Шаблоны зала **общие** для пула (без личных «только мне» в Скелете).

**UJ-3. Клиент регистрируется по ссылке и ведёт кабинет.**  
Тренер создаёт Клиента и отправляет Ссылку-приглашение (TTL). Клиент заполняет Имя, телефон, логин, пароль (валидация), попадает в кабинет, донастраивает профиль. Позже входит по логину или телефону + пароль. Видит единый Дневник независимо от того, кто из тренеров проводил Сессии.

**UJ-4. Пропуск, отмена и перенос.**  
У Тренировки в Ожидании Тренер может «Пропустить» или «Отменить» (оба сбрасывают Стрик; Отмена не списывает абонемент) либо **«Перенести»** на другую дату (стрик и абонемент не трогает).

**UJ-5. Другой тренер — в другой день (не одновременно).**  
Тренер А завёл программу и провёл Сессию. Позже Тренер Б открывает того же Клиента (когда тот не занят другим тренером в приложении), при необходимости правит программу и проводит Сессию. Понятия «ответственный тренер» нет — доступ равный. Запись клиентов на время в зале живёт вне приложения (бизнес-процесс).

## 3. Glossary

- **Пул клиентов** — единая база Клиентов зала; синхронизирована между всеми Тренерами (нет изолированных списков «мои клиенты», нет метки «ответственный тренер»).
- **Пул тренеров** — все Тренеры (и Админ) зала, имеющие равный доступ к Пулу клиентов.
- **Клиент** — посетитель зала из Пула клиентов с доступом к своему кабинету. Не закреплён за одним Тренером.
- **Тренер** — сотрудник из Пула тренеров: может открывать любого Клиента, править программу, назначать Тренировки и проводить Сессии — **не одновременно с другим Тренером на том же Клиенте**.
- **Занятость клиента (в приложении)** — состояние, когда один Тренер сейчас работает с карточкой/Сессией Клиента; второй Тренер в этот момент не может править того же Клиента.
- **Админ** — роль заказчика: все возможности Тренера плюс расширяемые привилегии (ачивки, управление Пулом тренеров и др.). Админ сам является Тренером.
- **Упражнение** — элемент каталога зала; может быть создано Тренером/Админом; у упражнения есть основная и дополнительные мышечные группы.
- **Шаблон тренировки** — переиспользуемое описание тренировки (название, тип, описание, упражнения, длительность, продолжительность в микроциклах).
- **Макроцикл** — объединение нескольких Шаблонов тренировки в повторяющийся цикл с заданной периодичностью.
- **Тренировка** — назначенный Клиенту экземпляр занятия в расписании (создаётся вручную Тренером/Админом).
- **Ожидание / Начать / Пропустить / Отменить** — действия над Тренировкой до или вместо проведения.
- **Статус Тренировки** — как минимум: **Ожидание**, **Пришёл**, **Пропущена**, **Отменена**; действие **Перенос** меняет дату/время Ожидания без Отмены.
- **Стрик тренировок** — по FR-20: Ожидание не ломает; **Пропущена** и **Отменена** сбрасывают; восстановление — после ≥2 подряд со статусом Пришёл; **Перенос** стрик не сбрасывает.
- **Сессия** — live-проведение Тренировки Тренером: таймер, подходы, отдых, суперсеты, модификаторы, итог.
- **Подход** — запись: вес, повторения, RPE; опционально Модификатор подхода.
- **Модификатор подхода** — метка на Подходе (пресет или кастом: название + цвет из RGB-матрицы), меняющая цвет отображения.
- **Суперсет** — связка упражнений без таймера отдыха между ними внутри связки; отдых — после завершения **полного круга** суперсета, не после каждого упражнения связки.
- **Дневник** — история Тренировок/Сессий Клиента с совместным доступом Тренера и Клиента (Клиент в основном читает): когда, какие упражнения, подходы, веса и т.д.
- **Ссылка-приглашение (регистрация)** — ссылка с **TTL**; анкета: Имя, телефон, логин, пароль (с валидацией полей). После регистрации — личный кабинет; далее вход по логину **или** телефону + пароль.
- **Абонемент (экземпляр у Клиента)** — активная выданная Клиенту карточка: остаток занятий, дата окончания, ссылка на План абонемента (или снимок параметров). Тренировка возможна и **без** Абонемента.
- **План абонемента** — настраиваемый тариф в каталоге зала (CRUD Админом/уполномоченным): название, цена, число занятий, срок (дни), длительность тренировки (мин), флаги (геймификация / ачивки / уровень статистики), описание, визуальные метаданные (цвет и т.п.). Хранится в БД, **не хардкодится** в клиенте. Актуальные офлайн-тарифы «Путеводитель» (рефы `docs/design-refs/abonement-guide-*.jpg`) заводятся в БД сидом/админкой после готовности CRUD.
- **Цель КБЖУ** — целевые калории/Б/Ж/У, задаёт Тренер.
- **Факт КБЖУ** — дневные цифры, которые вводит Клиент вручную (без базы продуктов).
- **Ранг** — уровень Клиента по числу тренировок со статусом Пришёл; пороги и значки настраивает Админ.
- **Скелет** — первая поставка (см. §6).
- **Этап 2** — следующие возможности продукта после Скелета.

## 4. Features

### 4.1 Роли, пулы и доступ

**Description:** Три роли — Клиент, Тренер, Админ. Модель зала: **Пул клиентов + Пул тренеров**. База общая: любой Тренер может работать с любым Клиентом (поочерёдно). Нет «ответственного тренера» и нет silo. **Одновременно** два Тренера не работают с одним Клиентом; один Тренер может переключаться между несколькими Клиентами. Запись на занятия в зале — вне продукта. Админ = Тренер + расширяемые привилегии. Realizes UJ-1, UJ-3, UJ-5.

**Functional Requirements:**

#### FR-1: Роли
Система различает Клиента, Тренера и Админа и ограничивает действия по роли.

**Consequences (testable):**
- Клиент не может стартовать Сессию и не может создавать Шаблоны/Макроциклы.
- Тренер может работать с Пулом клиентов и Сессиями, но не выполняет admin-only действия (например создание ачивок на Этапе 2).
- Админ может выполнять все действия Тренера и admin-only действия.

#### FR-2: Управление Пулом тренеров (Админ)
Админ может добавлять Тренеров в Пул тренеров и выдавать/передавать статус Админа.

**Consequences (testable):**
- Новый Тренер после создания сразу видит тот же Пул клиентов, что и остальные.
- Без роли Админа пользователь не может назначать Админов.

#### FR-2a: Общий Пул клиентов (без владельца)
Любой Тренер/Админ может открыть любого Клиента, править программу/назначения и проводить Сессии. Метки «ответственный тренер» нет.

**Consequences (testable):**
- Клиент, созданный Тренером А, сразу доступен Тренеру Б без «передачи».
- Нет UI/поля «ответственный тренер», ограничивающего доступ.
- В истории Сессии фиксируется, какой Тренер её провёл (author).
- В Дневнике доступна полная история **когда / какие упражнения / подходы / веса** (и связанный лог Сессий) — это обязательный «changelog» тренировочного процесса, не опциональный.

#### FR-2b: Эксклюзивная работа с Клиентом (не два тренера сразу)
Пока Тренер работает с Клиентом в приложении (карточка / редактирование программы / активная Сессия), другой Тренер не может одновременно править того же Клиента или вести по нему Сессию. Один Тренер может переключаться между Клиентами (в т.ч. работать последовательно с двумя).

**Consequences (testable):**
- Если Клиент уже занят Тренером А, Тренер Б получает отказ/блокировку с понятным сообщением (кто занял) и не может сохранить конкурирующие правки.
- Занятость снимается автоматически при **завершении Сессии** и при **уходе Тренера с карточки** Клиента после работы.
- Дополнительно: Тренер, удерживающий блокировку (и при необходимости любой Тренер/Админ из пула `[ASSUMPTION: force-unlock доступен занявшему; Админ тоже может force-unlock]`), может нажать **«Освободить»** (жёсткий сброс) — на случай сбоев.
- Также срабатывает **TTL = 30 минут бездействия** (нет heartbeat/активности). **Активная Сессия продлевает блокировку** — TTL не рвёт тренировку посередине по «стеночному» часу.
- После освобождения другой Тренер может взять того же Клиента.
- Тренер может переключаться между Клиентами без нарушения правила «два тренера на одного».
- Force-unlock: занявший Тренер и **Админ** могут жёстко освободить.

#### FR-3: Аутентификация Клиента
Клиент регистрируется по Ссылке-приглашению (анкета), далее входит по **логину или телефону + пароль**. Тренер/Админ — логин/пароль.

**Consequences (testable):**
- Неавторизованный пользователь не видит чужие Дневники.
- После регистрации по валидной ссылке Клиент сразу попадает в свой кабинет и может дополнять профиль/настройки.
- Повторный вход возможен и по логину, и по телефону (в паре с паролем).
- Поля регистрации и входа валидируются (обязательность, формат телефона, требования к паролю/логину — UX + architecture).

#### FR-3a: Аутентификация Тренера/Админа
Тренер и Админ входят по логину и паролю (без обязательного email).

### 4.2 Клиенты и приглашение

**Description:** Тренер/Админ создаёт Клиента в общем Пуле клиентов и отправляет Ссылку-приглашение. Realizes UJ-3, UJ-5.

#### FR-4: Создание Клиента
Тренер/Админ создаёт карточку Клиента в Пуле клиентов (карточка сразу общая для всего Пула тренеров).

#### FR-5: Ссылка-приглашение (регистрация)
Тренер/Админ создаёт Клиента (черновик/слот) и выдаёт Ссылку-приглашение с **TTL = 1 сутки** (по умолчанию). По ссылке открывается анкета регистрации: **Имя, номер телефона, логин, пароль**.

**Consequences (testable):**
- По валидной неистёкшей ссылке Клиент заполняет анкету (поля валидируются) и попадает в личный кабинет.
- Просроченная ссылка (TTL 1 день) не открывает регистрацию / не активирует кабинет.
- Тренер может **удобно скопировать** ссылку и отправить её Клиенту (один тап «копировать» / share) — без ручного набора URL.
- После успешной регистрации повторный вход — логин или телефон + пароль (FR-3).
- Правила сложности пароля/логина — на UX.

### 4.3 Каталог упражнений

**Description:** Каталог пополняется Тренерами/Админами. Для статистики мышц (Этап 2) у упражнения задаются основная и дополнительные группы (учёт 1:1 и 2:1).

#### FR-6: CRUD упражнений
Тренер/Админ может создавать и редактировать Упражнения (в т.ч. кастомные).

#### FR-7: Мышечные группы упражнения
У Упражнения задаются основная и дополнительные рабочие группы.

**Consequences (testable):**
- Новое Упражнение доступно для включения в Шаблон.
- Без указанных групп упражнение всё равно можно использовать в Скелете; предупреждение допустимо `[ASSUMPTION]`.

### 4.4 Шаблоны и макроциклы (Скелет)

**Description:** Конструктор Шаблона тренировки и Макроцикла. Realizes UJ-2.

#### FR-8: Шаблон тренировки
Тренер/Админ создаёт Шаблон: название, тип, описание, упражнения (с запланированными подходами), длительность, продолжительность в микроциклах.

**Consequences (testable):**
- Шаблоны общие для пула. Одновременное редактирование одного Шаблона двумя Тренерами: **last-write-wins** с предупреждением при конфликте версии `[ASSUMPTION: оптимистичный concurrency / version field — architecture]`. Блокировка FR-2b на Шаблоны не распространяется.

#### FR-9: Макроцикл
Тренер/Админ объединяет несколько Шаблонов в Макроцикл с периодичностью / порядком этапов. Прогресс по Макроциклу идёт **поэтапно**.

**Consequences (testable):**
- Макроцикл ссылается на существующие Шаблоны.
- У Клиента хранится указатель «текущий этап» Макроцикла; при назначении следующей Тренировки Тренер берёт следующий Шаблон по порядку (может скорректировать вручную).
- **Пропущена / Отменена / Перенос** указатель этапа сами по себе не двигают назад; после **Пришёл** указатель сдвигается на следующий этап `[ASSUMPTION: Тренер может вручную сдвинуть этап]`.
- Назначение в расписание — **по одной Тренировке** (когда известна дата визита), без массовой серии дат.
- Изменение Шаблона не ломает уже завершённые Сессии `[ASSUMPTION: снимок или стабильная ссылка — architecture]`.

### 4.5 Расписание тренировок Клиента (Скелет)

**Description:** Тренировки Клиента заводятся вручную по мере необходимости. Статусы/действия: Ожидание → Начать / Пропустить / Отменить / **Перенести**. Realizes UJ-1, UJ-4.

#### FR-10: Назначение Тренировки
Тренер/Админ создаёт одну Тренировку Клиенту на дату/время на основе следующего этапа Шаблона/Макроцикла или явного набора упражнений.

#### FR-11: Действия над Ожиданием
Для Тренировки в Ожидании доступны: Начать, Пропустить, Отменить, **Перенести**.

**Consequences (testable):**
- Пропуск → статус **Пропущена**; учитывается как пропуск; **сбрасывает Стрик**.
- Отмена → статус **Отменена**; не посещение и не «пропуск посещения» в аналитике посещений; **не** списывает Абонемент; **сбрасывает Стрик** (уточнение к раннему «не учитывается вовсе»: в статистике посещений не участвует, но на Стрик влияет — поэтому для сдвига даты использовать **Перенос**).
- **Перенос** → новая дата/время, статус **Ожидание**; Абонемент не списывается; Стрик не сбрасывается; пуш Клиенту не нужен (устно).
- Начать → создаётся Сессия; по завершении статус **Пришёл**.
- **Списание Абонемента** (Начать/Пропустить) реализуется вместе с модулем Абонемента (**Этап 2**, FR-30a). В Скелете статусы работают **без** обязательного модуля Абонемента; тренировки без Абонемента всегда допустимы.
- Тренировка без Абонемента допускается.

### 4.6 Сессия (live) (Скелет)

**Description:** Только Тренер/Админ стартует и ведёт Сессию. Клиенту live не обязателен — достаточно истории после. Realizes UJ-1.

#### FR-12: Старт Сессии
Тренер/Админ начинает Сессию по Тренировке; запускается **таймер длительности тренировки** (общий ход Сессии); порядок — с первого упражнения.

**Consequences (testable):**
- На экране Сессии виден идущий таймер тренировки (отдельно от таймера отдыха FR-14).
- Сессия начинается с первого упражнения Шаблона/назначения.

#### FR-13: Лог подхода
В Сессии для каждого подхода вводятся вес, повторения, RPE.

**Consequences (testable):**
- Каждый введённый Подход **сохраняется в БД** (не только в памяти экрана): вес, повторения, RPE, порядок, связь с упражнением и Сессией, Модификатор при наличии.
- Обрыв соединения / перезагрузка не должна терять уже подтверждённые подходы `[ASSUMPTION: автосохранение по подходу или эквивалент — architecture]`.

#### FR-14: Отдых
После упражнения (вне суперсета) запускается таймер отдыха.

#### FR-15: Суперсеты
Упражнения можно связать в Суперсет: между ними таймер отдыха не запускается; после подхода одного упражнения — переход к подходу другого; **отдых запускается после полного круга** суперсета.

#### FR-16: Модификаторы подхода
К Подходу можно добавить Модификатор (пресеты вроде дропсет / myo reps и **кастомные**).

**Consequences (testable):**
- Тренер/Админ может создать кастомный Модификатор: вписать название и выбрать цвет из RGB-матрицы.
- Выбранный Модификатор меняет цвет отображения Подхода в Сессии и в истории.
- Кастомные Модификаторы доступны повторно после создания `[ASSUMPTION: кастомные модификаторы общие для зала / Пула тренеров]`.

#### FR-17: Итог Сессии
По завершении показываются: число подходов, поднятый тоннаж, рост относительно прошлого выполнения.

**Consequences (testable):**
- Рост считается **по каждому упражнению** относительно последнего выполнения **этого же** Упражнения Клиентом (не относительно «прошлой Тренировки целиком»).
- Если в программе упражнение заменили на другое, рост нового считается от последнего раза, когда Клиент делал именно его.
- Метрика роста — изменение **общего тоннажа за упражнение** (сумма вес×повторы по подходам в этой Сессии vs в прошлом выполнении того же Упражнения), в процентах.
- Если упражнения ещё не было в истории — рост не показывается (или «первый раз»), без ошибки.

#### FR-18: История в Дневнике и персистентность тренировок
Все проведённые Тренировки/Сессии и их детальный лог **хранятся в базе** и доступны в Дневнике Клиенту и Тренерам из пула.

**Consequences (testable):**
- После завершения Сессии в БД есть: Сессия, список упражнений, все Подходы (вес, повторы, RPE, модификаторы), тоннаж/итоги, автор-Тренер, связь с Клиентом и исходной Тренировкой.
- Другой Тренер позже открывает того же Клиента и видит полную историю подходов/весов, а не только факт «тренировка была».
- Данные не пропадают после выхода из приложения / смены устройства (при наличии сети и успешного синка) `[ASSUMPTION: offline-очередь — architecture, если нужна]`.

**Feature-specific NFRs:**
- Mobile-first ввод в зале: крупные тач-зоны, минимум шагов, работа одной рукой (детали — UX).
- См. также FR-33 / NFR таймеров.

### 4.7 Кабинет Клиента — обзор тренировок (Скелет, частично)

**Description:** Вкладка тренировок: ближайшие, запланированная, счётчики. Полные стрики питания/ачивок — с Этапа 2.

#### FR-19: Обзор тренировок Клиента
Клиент видит количество тренировок в текущем месяце, календарь ближайших и какая Тренировка запланирована, плюс Стрик тренировок (FR-20).

#### FR-19a: Структура кабинета Клиента (вкладки)
Целевая навигация кабинета Клиента (как у заказчика):

1. **Тренировки** — обзор, стрик тренировок; стрик питания показывается здесь же, когда модуль Питания включён (Этап 2).
2. **Аналитика/статистика** — Этап 2 (FR-21…23).
3. **Питание** — Этап 2 (FR-24…26).
4. **Замеры** — Этап 2 (FR-27).
5. **Ачивки** — Этап 2 (FR-28…29a).
6. **Абонемент** — Этап 2 (FR-30a): Клиент видит остаток и дату на отдельной вкладке.

В Скелете достаточно вкладки/экрана **Тренировки** (+ вход в историю Сессии); остальные вкладки появляются с Этапом 2, но IA кабинета уже зафиксирована.

#### FR-20: Стрик тренировок
Клиент видит Стрик тренировок. Формула опирается на назначенные Тренировки и их статусы (не на календарные дни).

**Consequences (testable):**
- Пример: назначено 10 Тренировок; 5 в статусе Пришёл, 5 в Ожидании → Стрик = 5 (Ожидание не сбрасывает и не увеличивает).
- Статус **Пропущена** или **Отменена** → Стрик = 0.
- **Перенос** не сбрасывает Стрик.
- После сброса для нового роста нужно ≥2 подряд **Пришёл**: после первого Пришёл отображается Стрик = 0 (ещё копится); после второго подряд Пришёл Стрик = 2, далее +1 за каждый следующий Пришёл подряд.
- Отображение Стрика доступно в Скелете на обзоре тренировок; полный кабинет из 6 вкладок — FR-19a / Этап 2 для остальных вкладок.

### 4.8 Этап 2 — Аналитика

#### FR-21: Посещения и пропуски
Статистика посещённых и пропущенных за месяц / 3 месяца / год.

#### FR-22: Тоннаж и прогресс упражнений
Поднятые кг за период; прогресс выбранных упражнений во времени (тоннаж за упражнение относительно предыдущих выполнений того же Упражнения — согласовано с FR-17).

#### FR-23: Нагрузка на мышцы
Подходы в неделю на мышцу: основная группа 1:1, дополнительная 2:1.

### 4.9 Этап 2 — Питание

#### FR-24: Цель КБЖУ
Тренер задаёт Клиенту Цель КБЖУ.

#### FR-25: Факт КБЖУ
Клиент вводит Факт КБЖУ за день вручную (без поиска продуктов).

#### FR-26: Соблюдение и стрик питания
Недельный график соблюдения Цели и стрик учёта питания.

### 4.10 Этап 2 — Замеры

#### FR-27: Замеры тела
Клиент и Тренер/Админ могут вносить и редактировать замеры: вес, обхваты (руки, талия, бёдра, ягодицы, грудь) и кастомные метрики; видна динамика.

**Consequences (testable):**
- Тренер может редактировать замеры Клиента.
- Клиент может вносить свои замеры.

### 4.11 Этап 2 — Ачивки и ранг

#### FR-28: Каталог ачивок (Админ)
Админ создаёт/редактирует ачивки в админ-панели.

#### FR-28a: Открытие ачивок Клиенту (Тренер)
Тренер открывает (выдаёт) ачивки конкретному Клиенту.

#### FR-29: Витрина ачивок Клиента
Когда Клиент заходит в раздел ачивок, видит анимацию, после чего последовательно показываются открытые ачивки; также видны ещё не открытые, стрики и Ранг.

**Consequences (testable):**
- При входе в раздел запускается анимация раскрытия/показа.
- Открытые ачивки демонстрируются последовательно (не одним статичным списком без эффекта).
- Неоткрытые ачивки, стрики и Ранг доступны в том же разделе.

#### FR-29a: Ранги (Админ)
Админ в админ-панели настраивает ранги: добавление ранга, порог по количеству тренировок (статус Пришёл) для получения, значок ранга.

**Consequences (testable):**
- Ранг Клиента меняется автоматически при достижении порога по числу тренировок Пришёл.
- Без настройки Админа система не требует хардкода рангов в коде продукта.

### 4.12 Этап 2 — Абонементы (каталог + экземпляр)

#### FR-30: Каталог Планов абонемента (настраиваемый)
**Только Админ** может **добавлять, редактировать, архивировать** Планы абонемента. Все параметры хранятся в БД. Тренер выдаёт Клиенту экземпляр (FR-30a), но не редактирует каталог Планов.

**Параметры Плана (минимум, расширяемо):**
- название;
- цена (информативно; оплаты в продукте нет);
- число занятий (может отсутствовать у спец-планов вроде «бонус пасс»);
- срок действия в днях;
- длительность тренировки в минутах (если применимо);
- флаги возможностей: геймификация вкл/выкл, ачивки, уровень статистики и т.п.;
- доп. описание / примечание;
- визуальные метаданные (например цвет ленты/акцента).

**Consequences (testable):**
- В коде клиента/сервера **нет** захардкоженного списка тарифов «Тропа Начинающего» и т.д. — только данные из БД.
- После добавления нового Плана через админку он доступен для выдачи Клиенту без релиза приложения.
- Актуальные тарифы с фото «Путеводитель» переносятся в БД отдельным шагом (сид/ручной ввод), не как константы в репозитории.

#### FR-30a: Экземпляр Абонемента у Клиента и списание
Тренер/Админ выдаёт Клиенту Абонемент на основе Плана (или с ручной подстройкой остатка/дат `[ASSUMPTION: допускается ручная корректировка остатка при выдаче]`). Клиент видит остаток и дату окончания. Тренировки **без** Абонемента разрешены.

**Consequences (testable):**
- При **Начать** и при **Пропустить** с активного Абонемента списывается 1 занятие (остаток −1), если Абонемент есть и остаток > 0. Если остаток **0** — система **предупреждает**, но **не запрещает** Начать/Пропустить; остаток не уходит в минус.
- При **Отменить** и при **Перенести** занятие с Абонемента **не** списывается.
- Если Абонемента нет — действия работают без списания.
- План без лимита занятий (если так задан) не уменьшает «число занятий» `[ASSUMPTION: для бонус-пассов без тренировок списание занятий не применяется]`.

**Out of Scope внутри фичи:** онлайн-оплата, платёжные методы, расчёт выручки/ЗП. Цена на Плане — справочная.

### 4.13 Дизайн и UX-рамка (кросс-срез)

#### FR-31: Mobile-first UI
Основные сценарии Скелета удобны на телефоне в зале.

#### FR-32: Визуальный язык «Гильдия»
UI следует палитре/типографике направления Гильдия (см. design brief); без лишних декоративных элементов, мешающих тренировочному потоку.

#### FR-33: Персональные данные (минимум)
Продукт обрабатывает ПДн Клиента (телефон, замеры и т.п.) в рамках одного зала. Минимально: доступ по ролям, без публичной индексации кабинетов. Детали 152-ФЗ / хранение / согласия — на architecture + при необходимости юр. консультации `[NOTE FOR PM]`.

**Feature-specific NFRs (Сессия):**
- Таймер отдыха и таймер тренировки в **веб-приложении** на мобильном должны корректно переживать уход вкладки/блокировку экрана (абсолютный deadline, не только setInterval) — architecture/UX.

## 5. Non-Goals (Explicit)

- SaaS для множества залов, маркетплейс тренеров.
- Изолированные кабинеты «один тренер — только свои клиенты»; метка/роль «ответственный тренер».
- Запись/бронирование клиентов на слоты **в приложении** (в зале запись существует как бизнес-процесс вне продукта).
- Расчёт ЗП, выручки, финансовые отчёты, онлайн-оплата.
- База продуктов / штрихкоды / FatSecret и аналоги — не цель продукта.
- Обязательный realtime-просмотр Сессии Клиентом.
- Одновременное редактирование одного Клиента двумя Тренерами.
- Чат и комментарии к Тренировке — не нужны, достаточно устного общения.
- Хардкод тарифов/ачивок/рангов в коде — всё настраиваемо через данные.
- Push/уведомления Клиенту при Переносе и прочие push в Скелете — не усложняем (устное общение).
- Нативное iOS/Android приложение как обязательство — нет; целевая платформа: **веб-приложение** (mobile-first).

## 6. MVP Scope

### 6.1 In Scope — Скелет

- Роли Клиент / Тренер / Админ; **Пул клиентов + Пул тренеров** (общая база, без владельца клиента); **эксклюзивная занятость клиента** при работе тренера; вход; создание Клиента + Ссылка-приглашение.
- Каталог Упражнений (создание Тренером/Админом).
- Шаблоны тренировки + Макроциклы.
- Ручное назначение Тренировок по одной (поэтапно по Макроциклу); Ожидание / Начать / Пропустить / Отменить / **Перенести**.
- Сессия: **таймер длительности** + подходы (вес, повторы, RPE), отдых, суперсеты, модификаторы **включая кастом (название + RGB)**, итог с ростом тоннажа по упражнению; **полная персистентность в БД** (FR-12…18).
- Дневник/история для Клиента и Тренера с детальными подходами/весами.
- Обзор вкладки **Тренировки** + Стрик; IA кабинета из 6 вкладок зафиксирована (остальные — Этап 2).
- Mobile-first веб-UI в духе «Гильдия».

### 6.2 Out of Scope for MVP → Этап 2

- Аналитика мышц, тоннаж/прогресс-графики, посещения за периоды (FR-21…23).
- Питание (FR-24…26).
- Замеры с правом Тренера редактировать (FR-27).
- Ачивки (каталог Админ, открытие Тренером, анимация витрины + последовательный показ) и настраиваемые Ранги (FR-28…29a).
- **Каталог Планов абонемента** (CRUD админ, БД) + вкладка/экземпляр + списание Начать/Пропустить (FR-30, FR-30a); сид «Путеводитель» после админки.
- В Скелете статусы работают без модуля Абонемента.

## 7. Success Metrics

*Внутренний инструмент — качественные метрики достаточны.*

**Primary**
- **SM-1**: Тренеры реально проводят Сессии в зале через продукт (не на бумаге) на протяжении ≥4 недель подряд после запуска Скелета. Validates FR-12…18.
- **SM-2**: Клиент с активированным доступом может без помощи найти последнюю Тренировку и её итог. Validates FR-18, FR-19.

**Secondary**
- **SM-3**: Время от открытия Ожидания до первого залогированного подхода — приемлемо в зале (субъективно тренера; UX-проверка). Validates FR-12…13.

**Counter-metrics**
- **SM-C1**: Не оптимизировать число экранов/ачивок в ущерб скорости Сессии. Counterbalances будущий Этап 2 геймификации.
- **SM-C2**: Не раздувать Скелет Этапом 2 до стабильного проведения тренировок.

## 9. Assumptions Index

- Платформа: **веб-приложение**, mobile-first.
- Суперсет: отдых после полного круга.
- Шаблоны общие; конфликт правок Шаблона — last-write-wins.
- Блокировка Клиента: TTL **30 мин бездействия**; активная Сессия продлевает; снятие при конце Сессии + уход с карточки; «Освободить»; Админ может force-unlock.
- Ссылка регистрации TTL = **1 день**; копирование; вход логин|телефон + пароль; пароль → UX.
- Списание Абонемента — с Этапом 2; Скелет без обязательного модуля Абонемента.
- Отмена сбрасывает Стрик (не «игнор полностью»); Перенос — способ сдвинуть без сброса.
- После сброса стрика: 1-й Пришёл → 0; 2-й подряд → 2.
- Макроцикл: указатель этапа у Клиента; одна Тренировка в расписание.
- CRUD Планов — только Админ.
- Кабинет Клиента: 6 вкладок (IA); в Скелете минимум «Тренировки».
- Таймер длительности Сессии + таймер отдыха.
- Author + полная история подходов в БД.
- Push при Переносе не нужен.
- Чат не нужен.
- 152-ФЗ детали — OQ/architecture.

## 10. Delivery notes (process)

- Разработка через оркестрацию: чёткие задачи саб-агентам без додумывания вне AC.
- TDD: тест → red → код.
- Технические развилки (стек BFF, деплой, таймер в фоне, точное значение TTL) **спрашивать отдельно**, не зашивать молча в story.
- Репозиторий: `frontend/` + `backend/`, React + TypeScript, BFF — см. `docs/project-spec.md`.
