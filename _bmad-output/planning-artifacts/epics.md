# quest-fitness - Epic Breakdown

## Overview

This document provides the complete epic and story breakdown for quest-fitness, decomposing the requirements from the PRD, UX Design if it exists, and Architecture requirements into implementable stories.

## Requirements Inventory

### Functional Requirements

**Скелет (PRD §6.1) — реализуется поведением:**

FR-1: Система различает роли Клиент / Тренер / Админ и ограничивает действия по роли (Клиент не стартует Сессию и не создаёт Шаблоны/Макроциклы; Админ ⊇ Тренер + admin-only).
FR-2: Админ добавляет Тренеров в Пул тренеров и выдаёт/передаёт статус Админа.
FR-2a: Общий Пул клиентов без владельца: любой Тренер/Админ открывает любого Клиента; метки «ответственный тренер» нет; в истории Сессии фиксируется author-Тренер; Дневник — полный changelog подходов/весов.
FR-2b: Эксклюзивная работа с Клиентом: второй Тренер не правит/не ведёт Сессию параллельно; снятие лока при завершении Сессии, уходе с карточки, TTL 30 мин бездействия; активная Сессия продлевает лок; «Освободить» (force-unlock) держателем и Админом.
FR-3: Клиент регистрируется по Ссылке-приглашению; далее вход логин **или** телефон + пароль; чужие Дневники недоступны без auth.
FR-3a: Тренер/Админ входят по логину и паролю (без обязательного email).
FR-4: Тренер/Админ создаёт карточку Клиента в общем Пуле клиентов.
FR-5: Ссылка-приглашение TTL = 1 сутки; анкета Имя, телефон, логин, пароль; копирование/share одним тапом; просроченная ссылка не активирует кабинет.
FR-6: Тренер/Админ CRUD Упражнений (в т.ч. кастомных).
FR-7: У Упражнения задаются основная и дополнительные мышечные группы; без групп упражнение usable в Скелете (предупреждение допустимо).
FR-8: Шаблон тренировки: название, тип, описание, упражнения с плановыми подходами, длительность, продолжительность в микроциклах; шаблоны общие; конфликт правок — LWW с предупреждением версии; блокировка FR-2b на Шаблоны не распространяется.
FR-9: Макроцикл объединяет Шаблоны с периодичностью/порядком; прогресс поэтапный; указатель этапа у Клиента; назначение по одной Тренировке; Пропущена/Отменена/Перенос указатель сами не двигают назад; после Пришёл — сдвиг; правка Шаблона не ломает завершённые Сессии.
FR-10: Тренер/Админ назначает одну Тренировку Клиенту на дату/время из следующего этапа или явного набора упражнений.
FR-11: Для Ожидания: Начать / Пропустить / Отменить / Перенести; Пропуск→Пропущена (сброс Стрика); Отмена→Отменена (не списывает Абонемент, сбрасывает Стрик); Перенос→новая дата, статус Ожидание (стрик/абонемент не трогает); Начать→Сессия→по завершении Пришёл; тренировка без Абонемента допустима; списание Абонемента — Этап 2.
FR-12: Старт Сессии Тренером/Админом; таймер длительности тренировки; старт с первого упражнения.
FR-13: Лог подхода: вес, повторения, RPE; каждый подтверждённый Подход сохраняется в БД (порядок, упражнение, Сессия, Модификатор).
FR-14: После упражнения вне суперсета запускается таймер отдыха.
FR-15: Суперсет: между упражнениями связки отдых не запускается; отдых после полного круга.
FR-16: Модификатор подхода: пресеты + кастом (название + цвет из палитры 6–8 оттенков ≥3:1 к surface-session-sunken, не free RGB — UX-DR22); меняет цвет отображения; кастомные доступны повторно пулу.
FR-17: Итог Сессии: число подходов, тоннаж, рост % тоннажа по каждому упражнению vs последнее выполнение того же Упражнения Клиентом; без истории — «первый раз».
FR-18: Все Сессии/логи персистентны в БД и доступны в Дневнике Клиенту и Тренерам пула (автор, подходы, веса).
FR-19: Клиент видит тренировки текущего месяца, календарь ближайших, запланированную Тренировку, Стрик (FR-20).
FR-19a: IA кабинета — 6 вкладок (Тренировки | Аналитика | Питание | Замеры | Ачивки | Абонемент); в Скелете рабочая — Тренировки (+ история Сессии); остальные — заготовки Этапа 2.
FR-20: Стрик тренировок по статусам назначенных Тренировок (не календарным дням): Ожидание прозрачен; Пропущена/Отменена → 0; Перенос не сбрасывает; после сброса: 1-й Пришёл → 0, 2-й подряд → 2, далее +1.
FR-31: Основные сценарии Скелета удобны на телефоне в зале (mobile-first).
FR-32: UI следует визуальному языку «Гильдия».
FR-33: ПДн: доступ по ролям; без публичной индексации кабинетов (минимум для Скелета).

**Этап 2 (PRD §6.2) — в Скелете только stubs/hooks по AD-9, без бизнес-логики:**

FR-21: Статистика посещённых и пропущенных за месяц / 3 месяца / год.
FR-22: Тоннаж и прогресс упражнений за период.
FR-23: Нагрузка на мышцы (основная 1:1, дополнительная 2:1).
FR-24: Тренер задаёт Клиенту Цель КБЖУ.
FR-25: Клиент вводит Факт КБЖУ за день вручную.
FR-26: Недельный график соблюдения Цели и стрик питания.
FR-27: Замеры тела (вес, обхваты, кастом) — Клиент и Тренер/Админ; динамика.
FR-28: Админ CRUD каталога ачивок.
FR-28a: Тренер открывает (выдаёт) ачивки Клиенту.
FR-29: Витрина ачивок с анимацией и последовательным показом; неоткрытые, стрики, Ранг.
FR-29a: Админ настраивает ранги (порог по Пришёл, значок); автосмена ранга по порогу.
FR-30: Админ CRUD/архив Планов абонемента в БД (без хардкода тарифов).
FR-30a: Выдача экземпляра Абонемента; списание при Начать/Пропустить; не при Отменить/Перенести; остаток 0 — предупреждение, не запрет; тренировки без Абонемента разрешены.

### NonFunctional Requirements

NFR-1: Mobile-first ввод в зале — крупные тач-зоны (≥48 px), минимум шагов, сценарии одной рукой (PRD §4.6 / FR-31; AD-11).
NFR-2: Таймер отдыха и таймер длительности Сессии переживают уход вкладки/блокировку экрана через абсолютный `endsAt`, не только setInterval (PRD §4.13; AD-8).
NFR-3: Запись Подходов — online-required; при сбое сети явная ошибка + retry; offline-очереди / локальной БД клиента / merge нет (AD-14; перекрывает PRD OQ offline).
NFR-4: Каждый подтверждённый Подход немедленно в Postgres; перезагрузка восстанавливает Сессию из БД; идемпотентность по клиентскому `setId` (AD-8).
NFR-5: Auth — серверная сессия + httpOnly cookie same-site; пароли argon2id; CSRF на мутации; сессии в Postgres (AD-5).
NFR-6: Кабинеты: HTML `noindex,nofollow`; логи без ПДн (FR-33; conventions).
NFR-7: Реализация — TDD: тест → red → green → refactor; критичные инварианты (lock, invite consume, set upsert, streak fold, session abandon) — обязательные тесты (AD-18; project-spec).
NFR-8: Единый error envelope `{ error: { code, message, details? } }`; FE ветвится только по `code` (conventions).
NFR-9: Календарные производные (месяц, «просрочена», TTL инвайта, границы стрика) считает BFF в `GYM_TIMEZONE` (default `Europe/Moscow`); FE не выводит семантику из TZ браузера (AD-17).
NFR-10: Единица поставки — Docker Compose (`frontend`, `backend`, `postgres:16`); миграции `prisma migrate deploy`; хостинг prod Deferred (AD-13).

### Additional Requirements

**Стартовый каркас (Epic 1 / Story 1):** greenfield по Structural Seed spine — не внешний starter-template; репозиторий `frontend/` + `backend/`; стек: Node 22 LTS, NestJS 12.1.1, Prisma 7.10.0, PostgreSQL 16, React 19.3.0, Vite 8.3.1, TypeScript 5.9.x, Vitest 3.x, OpenAPI 3.0.x → openapi-typescript 7.13.0 + openapi-fetch 0.17.0.

- AD-1/AD-2: FE только через codegen из `backend/openapi/openapi.yaml` (коммитится); сборка FE падает без контракта.
- AD-3: Модульный монолит Nest-модулей (`auth`, `users`, `invites`, `clients-lock`, `exercises`, `templates`, `macrocycles`, `workouts`, `sessions`, `diary`); без Redis/Kafka/websockets/очередей в Скелете.
- AD-4: Роли `client` | `trainer` | `admin`; нет поля владельца у Client; `authorTrainerId` на Session.
- AD-5: Инвайт — opaque-токен как хеш, TTL 1 сутки, однократное погашение; телефон E.164; логин lowercase; seed первого Админа из env; сброс пароля Клиента Админом + перевыпуск инвайта в Скелете.
- AD-6: ClientLock в Postgres; явный `POST …/lock`; heartbeat ≤60 с; idle-TTL 30 мин; soft-release с abandoned при незавершённой Сессии; 60 мин без set/heartbeat → abandoned; GET не захватывает лок.
- AD-7: Template `version` + 409 `TEMPLATE_VERSION_CONFLICT`; snapshot плана на старте Сессии; `ClientMacroProgress.currentStageId` = FK на `MacrocycleStage`; сдвиг указателя только `workouts` при `attended` (+ override Тренера).
- AD-8/AD-14: max один in-flight Подход + явный retry; `sequenceIndex`/`supersetGroupId` назначает сервер; таймеры только клиентские `endsAt`.
- AD-9: Этап 2 — только пустые Nest-модули / nullable-FK / stub-вкладки «Скоро»; хуки списания абонемента no-op.
- AD-10: Доменные инварианты только на backend.
- AD-15: Session `active` | `completed` | `abandoned`; completed→Workout `attended`; abandoned→Workout `pending`; abandoned читается в Дневнике как «не завершена»; не влияет на стрик/этап/абонемент.
- AD-16: Стрик — derived on demand в `workouts`; колонки/кеша нет; FE не пересчитывает.
- AD-19: Soft-delete упражнений/модификаторов (`archivedAt`); люди — `deactivatedAt`.
- AD-20: Статусы Workout пишет только `workouts`; `diary` — read-only; Idempotency-Key на статусных POST (кроме setId).
- FSD на FE: `app` / `pages` / `widgets` / `features` / `entities` / `shared` (api generated only).
- Процесс (project-spec): не додумывать вне AC/spine/PRD/UX; техвопросы спрашивать отдельно; конфликт артефактов → ARCHITECTURE-SPINE.
- Deferred вне Скелета: хостинг prod, CI/CD полный, 152-ФЗ детали, offline-очередь, поведение FR-21..30a.

### UX Design Requirements

UX-DR1: Внедрить design tokens Гильдии из DESIGN.md (colors, typography Rubik, spacing, rounded) как единый источник в `frontend` shared/ui; запрет градиентов/стекла/фиолетового/свечений/эмодзи-иконок.
UX-DR2: Dual surface: светлые экраны (`surface-app` / `surface-card`) vs тёмная live-Сессия (`surface-session*`); один красный акцент `#C33F46` в кадре.
UX-DR3: Компонент `button-primary` / `button-secondary` / `button-secondary-session` / `button-danger` с каноническими подписями действий verbatim: Начать, Пропустить, Отменить, Перенести, Освободить (без квестового языка на кнопках).
UX-DR4: Компонент `bottom-cta` — закреплённая нижняя полоса + safe-area; max один primary (+ optional secondary 60/40); ширина = `content-max` 640 px, не viewport.
UX-DR5: Компонент `client-row` + декоративный `lock-badge` в пуле; интерактивный lock/TTL/Освободить — только в шапке Карточки Клиента (hit ≥48 px).
UX-DR6: Компонент `streak-chip` (абрикос; при 0 — крем + «копится»); без анимаций/конфетти.
UX-DR7: `tab-bar` кабинета: 6 вкладок иконка+подпись; активная — красный индикатор; Этап 2 — `ink-soon` + «Скоро» без opacity.
UX-DR8: `soon-stub` — крем-панель с квестовым заголовком + одна строка; без демо-данных/графиков; отдельные формулировки на вкладку (когда пишутся).
UX-DR9: `status-pill` для Ожидание / Пришёл / Пропущена / Отменена — слово первично; красным статусы не красить.
UX-DR10: `input` + `field-error` (ошибка под полем `ink-error`, не accent-red CTA); форма не очищается; фокус на первое ошибочное поле.
UX-DR11: `bottom-sheet` / `confirm-dialog` / `trainer-menu`: один уровень; `role="dialog"` + focus trap + Esc; на ≥768 px меню остаётся шторкой (не sidebar/dropdown).
UX-DR12: `session-set-logger`: один активный Подход; степперы 2.5 кг / 1 повтор / 0.5 RPE; tabular-nums; маркер «Подход — сейчас» + рамка 2 px (красный не единственный cue); Enter подтверждает только внутри логгера.
UX-DR13: `rest-timer` + таймер длительности на абсолютном `endsAt`; пропуск / +30 с; истечение — текст + вибрация (если есть); `prefers-reduced-motion` → дискретные обновления.
UX-DR14: Индикатор сохранения в шапке Сессии: сохранено · сохраняется · не сохранилось, повторить; max один in-flight; блок нового confirm до успеха/retry (AD-8/AD-14).
UX-DR15: `invite-share`: копирование одним тапом + TTL «ссылка живёт 1 сутки»; текстовое подтверждение копирования (не тост поверх CTA).
UX-DR16: Layout: одна колонка ≤640 px всегда; margin 16/24; touch-min 48; viewport min 360×640; без сайдбаров/дашбордов.
UX-DR17: Состояния: пустой пул («Гильдия пока собирается»), занятый клиент (чтение + баннер + aria-disabled мутаций), confirm перед Пропустить/Отменить/Освободить с альтернативой Перенести, LWW-диалог Шаблона, истёкший инвайт, восстановление Сессии после reload.
UX-DR18: A11y floor: контраст ≥4.5:1 текст / ≥3:1 границы; live regions polite для save/copy/TTL; timer без посекундных объявлений; 200% на 320 px; `forced-colors`; `lang="ru"`; один h1 на поверхность.
UX-DR19: Interaction: без swipe-delete; reorder «выше/ниже»; pull-to-refresh + revalidate on focus; тихий poll пула ~30 с; запрет тостов поверх CTA, модалок поверх Сессии, push, каруселей, звука.
UX-DR20: Знак Гильдии 24–32 px монохром в шапке/иконке; квестовый язык только в заголовках/empty/soon; Voice & Tone канон из EXPERIENCE (verbatim статусы и сообщения ошибок).
UX-DR21: Валидация auth (locked A1): логин 3–32 латиница/`_`/`-`/цифры; пароль ≥8; правила до submit; BFF зеркалит (AD-5).
UX-DR22: Палитра кастомных Модификаторов — 6–8 предпроверенных оттенков ≥3:1 к `surface-session-sunken` (не свободный RGB; при расхождении со wording «RGB» в spine побеждает UX a11y); точка + ярлык + accessible name.
UX-DR23: Навигация Тренера: старт = Пул клиентов; каталог/шаблоны/макроциклы/админ — из `trainer-menu`; у Тренера нет нижнего tab bar.

## Epic List

### Epic 1: Каркас зала и вход
Команда поднимает продукт локально; Тренер/Админ/Клиент входят по cookie-сессии; роли режут доступ; shell Гильдии и noindex на месте.
**FRs covered:** FR-1, FR-3 (вход), FR-3a, FR-31, FR-32, FR-33

### Epic 2: Пул клиентов, приглашения и занятость
Тренер заводит Клиента и Ссылку-приглашение; Клиент регистрируется; общий пул; эксклюзивный лок + TTL + «Освободить»; Админ минимально заводит Тренера / выдаёт Админа. Soft-release/force-unlock → Session abandoned (AD-15).
**FRs covered:** FR-2, FR-2a, FR-2b, FR-3 (регистрация), FR-4, FR-5

### Epic 3: Каталог и программы зала
Тренер ведёт Упражнения, общие Шаблоны (LWW) и Макроциклы с указателем этапа у Клиента.
**FRs covered:** FR-6, FR-7, FR-8, FR-9

### Story 1.1: Каркас платформы (Docker + Nest/Prisma/React + OpenAPI)

As a разработчик зала,
I want поднять `frontend` + `backend` + Postgres одной командой с каноническим OpenAPI и codegen,
So that дальше можно наращивать домен без второго контракта и без выдуманного стека.

**Acceptance Criteria:**

**Given** чистый клон репозитория
**When** выполняется `docker compose up` по инструкции в корневом README
**Then** поднимаются контейнеры `frontend`, `backend`, `postgres:16` (AD-13)
**And** корни репозитория — только `frontend/` и `backend/` (AD-1)
**And** README описывает compose-команды, необходимые env (включая `SEED_ADMIN_*`, `DATABASE_URL`, `SESSION_SECRET`, `GYM_TIMEZONE`) и проверку health

**Given** backend на NestJS 12.1.1 + Prisma 7.10.0 + Node 22 LTS (AD-12)
**When** применяются миграции и seed
**Then** Postgres доступен только через Prisma; `prisma/seed.ts` читает `SEED_ADMIN_LOGIN` + `SEED_ADMIN_PASSWORD` (дефолтного пароля в репо нет)
**And** схема меняется только миграциями Prisma

**Given** пайплайн контракта
**When** выполняется export OpenAPI и FE codegen
**Then** канон — `backend/openapi/openapi.yaml` (OpenAPI 3.0.x), файл **коммитится в git** (AD-2)
**And** клиент генерируется только в `frontend/src/shared/api`; сборка FE падает, если YAML отсутствует или codegen ломается
**And** второй ручной YAML / обход codegen запрещены

**Given** локальный Vite
**When** FE обращается к API
**Then** same-site через Vite proxy на `/api` (AD-5/AD-13); CORS с credentials не настраивается

**Given** TDD (AD-18)
**When** каркас готов
**Then** Vitest подключён в BE (заготовка FE); smoke-тест app/health проходит green

### Story 1.2: Серверная сессия и вход Тренера/Админа

As a Тренер или Админ,
I want войти и выйти по логину и паролю с httpOnly cookie,
So that я безопасно попадаю в рабочую оболочку зала и могу завершить сессию.

**Acceptance Criteria:**

**Given** seeded Админ из `SEED_ADMIN_*`
**When** он отправляет логин + пароль
**Then** создаётся серверная сессия в Postgres; cookie `qf_session`: httpOnly, SameSite=Lax, Path=/, Secure вне `local` (AD-5)
**And** пароль проверен argon2id (memoryCost≥65536)
**And** после успеха landing — экран **Пул клиентов** (UX-DR23)

**Given** мутирующие маршруты
**When** запрос идёт без CSRF-токена
**Then** глобальный Nest CSRF-guard отклоняет его (механизм: custom-header / double-submit на все мутации)
**And** сгенерированный клиент использует `credentials: 'same-origin'`

**Given** авторизованный Тренер/Админ
**When** вызывает logout
**Then** серверная сессия инвалидируется; cookie сбрасывается; повторный доступ к защищённым маршрутам требует нового входа

**Given** неверные учётные данные
**When** пользователь пытается войти
**Then** error envelope с кодом из enum (`UNAUTHENTICATED` / `VALIDATION_FAILED`); FE ветвится только по `code` (NFR-8)
**And** поля формы не очищаются (UX-DR10)

**Given** рестарт backend
**When** cookie сессии ещё валидна
**Then** пользователь остаётся залогинен (сессии в Postgres, не in-memory)

**Given** Vitest
**When** пишутся тесты login / logout / session create
**Then** red→green; пароль не попадает в логи

### Story 2.5: Эксклюзивная блокировка, TTL, Освободить, abandoned

As a Тренер,
I want явно взять Клиента, держать лок с heartbeat и освобождать (в т.ч. force),
So that два Тренера не правят одного Клиента одновременно, и брошенный лок не тупик.

**Acceptance Criteria:**

**Given** карточка на чтение
**When** Тренер жмёт «Взять клиента» → `POST /clients/:id/lock`
**Then** атомарный захват; ответ с серверным `expiresAt` (единственный отсчёт UI); мутации без лока → `LOCK_REQUIRED` (AD-6)

**Given** чужой живой лок
**When** другой Тренер пытается захватить / мутировать
**Then** `409 CLIENT_LOCKED` (`holderTrainerId`, `expiresAt`); баннер «Клиента ведёт … Освободится через …»; мутации `aria-disabled` + `aria-describedby` (UX-DR17)

**Given** держатель на карточке/Сессии
**When** heartbeat не реже 60 с
**Then** `lastActivityAt` обновляется; idle-TTL = 30 мин; за 5 мин до TTL — тихая строка (не показывается в активной Сессии)

**Given** уход с карточки (soft-release) при незавершённой Сессии
**When** `DELETE` lock
**Then** в одной транзакции: Session → `abandoned`, Workout → `pending`, лок снят (AD-15); уход всегда освобождает Клиента
**And** `pagehide`+keepalive — best-effort; гарантия — TTL

**Given** force-unlock «Освободить» (держатель или Админ)
**When** confirm «Освободить клиента? Правки … могут не сохраниться.»
**Then** лок снят; при active Session → `abandoned` (AD-15); второй Тренер **не** продолжает тот же `sessionId`
**And** кнопка `button-danger`; подтверждение обязательно (UX-DR3)

**Given** 60 мин без записи Подхода и без heartbeat при active Session
**When** срабатывает серверный idle
**Then** Session → `abandoned`, далее лок истекает обычным TTL (AD-6/AD-15)

**Given** Vitest
**When** тесты acquire / conflict / release / force-unlock→abandoned
**Then** обязательный red→green
